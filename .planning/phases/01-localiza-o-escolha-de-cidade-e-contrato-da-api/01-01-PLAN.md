<objective>
Stand up the greenfield Flutter project and prove the whole Clean Architecture stack end-to-end
with the thinnest real capability: open the app → see served cities loaded from a real bundled
data source → tap one → the choice persists on-device → the next cold start opens in the saved
city. This is the Walking Skeleton and the phase tracer.

Purpose: prove scaffold → data source → repository → DI → use case → UI → local persistence works
end-to-end before any location logic is layered on. Establishes the test harness the rest of the
phase depends on (Wave 0).
Output: a runnable Flutter app (Android/iOS), the mandated stack wired at exact versions, the
sealed `Result<T>`, the `Cidade` model/entity, the local + prefs data sources behind a
DI-registered `CidadeRepository`, and a minimal city-selection screen. LOC-04 satisfied.
</objective>

<user_story>
**As a** visitante, **I want to** escolher minha cidade e ter essa escolha guardada no aparelho,
**so that** o app reabre direto na minha cidade sem me pedir conta, senha ou nova escolha.
</user_story>

<assumption_delta_decision>
Primary noun: **city identity**. Transition considered: numeric `id` (as returned by the DB /
future `GET /cidades`) vs. the `nome+uf` natural key.
Decision: **chosen — persist by `nome+uf` natural key** (promote the natural key over the numeric
id for the stored value). Rationale: the fixed asset's ids will not match the real API's ids once
Phase 2 lands, and `Cidade` has `unique(nome, uf)`; the natural key resolves stably across the
fixture→API transition (D-15). Advisory, non-blocking.
</assumption_delta_decision>
